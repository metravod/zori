# Decisions

- D1 [accepted 2026-11-14] Port the level-based scheduler from zymi-core and write a process driver for CLI agents. This keeps flows independent of the upstream runtime. → [DAG planner](../src/dag.rs)
- D2 [accepted 2026-11-14] Use the name Zori for this standalone agent orchestration project. → [project brief](brief.md)
- D3 [accepted 2026-11-14] A failed task skips dependent branches while independent tasks continue. Level barriers keep the execution order predictable. → [runner](../src/runner.rs)
- D4 [accepted 2026-11-14] Optional branches may fail without blocking a join. Downstream prompts explicitly identify the missing result. → [configuration](../src/config.rs)
- D5 [accepted 2026-11-15] Drive agents through their CLIs. ZCode's bundled CLI has no per-run model selection, so headless ZCode stays outside the supported v0 agents. → [connectors](../src/connectors.rs)
- D6 [accepted 2026-11-16] Both runners execute level siblings concurrently, capped by max_parallel, using a snapshot of completed upstream outputs. → [runner](../src/runner.rs)
- D7 [accepted 2026-11-16] One run tree stores per-task working directories, attempts, logs and a provenance manifest for both runners. → [artifacts](../src/artifacts.rs)
- D8 [accepted 2026-11-18] Design a per-task Git worktree mode for parallel edits, with changes passed to downstream tasks as patches. Implementation is pending. → [worktree design](threads/worktree-isolation.md)
- D9 [accepted 2026-11-18] Supervise tracked attempts with bounded retries, session nudges and operator questions. → [watchdog](../src/watchdog.rs)
- D10 [accepted 2026-11-22] Workflow skills (onboarding, feat/bugfix discipline, review roles) live in the operator's `~/.zori/skills/`, not in the repo. Built-ins stay limited to zori's own tool knowledge (`zori-config`, `zori-planner`); a personal file of the same name shadows a built-in by design. → [skills.rs](../src/skills.rs), [log](log.md)
- D11 [accepted 2026-11-22] Split zori's stores by audience: the personal home `~/.zori/` holds machine-personal state — the global skills store, the model fleet (`fleet.json`) and the personal harness registry (`harnesses.yml`); runs, saved flows and per-project `zori-skills/` stay in the project because runs are artifacts of a checkout (`workspace: flow`, relative paths, private material). Planner chats prefer the fleet's models via a brief section; personal harnesses resolve built-in → personal → flow everywhere (picker, Fleet, planner brief, CLI listings). → [fleet.rs](../src/fleet.rs), [connectors.rs](../src/connectors.rs), [guide](../docs/guide.md)
- D12 [accepted 2026-11-24] Node-level operations follow the operator's model: stop run/node → `Stopped` status keeping the session handle so steer resumes the same session; steer allowed on Done/Stopped/Failed; per-task `approve: true` parks the node for human review before downstream proceeds (Reject = steer-feedback or rerun-with-fix). No add-node, no fork-from-node, no auto stale-cascade, no event-sourced runtime (D1 stands). → [thread](threads/node-level-operations.md)
- D13 [accepted 2026-11-25] Merged the classic runner (`zori run`) into `TrackedRun`: the terminal and the console share one engine, with one spawn path (`spawn_captured`) and the same watchdog, retries and questions; D12 gets built once. Rejected: keeping both engines. Done on branch `refactor/one-engine` (not yet merged into main) → [review](threads/code-review-2026-11-24.md), [follow-ups](threads/one-engine-followups.md)
- D14 [open 2026-11-25] Front-end foundation for the console redesign: split `web/index.html` into native ES modules with no bundler (still embedded in the binary), or adopt a light framework with a build step. One 3443-line file makes the compare view, inbox and live cards expensive to build. Waits for the human. → [thread](threads/console-ui-redesign.md)
